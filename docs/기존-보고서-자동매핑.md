# 기존 보고서 자동 매핑과 위키 편입

기존 HWP·PDF·텍스트 보고서나 DB 원문 행을 서버에 등록하면, 모델이 CLEW의 공통 필드를 **원문 그대로 추출**하고 코드가 필드별 근거를 확인합니다. 매핑된 결과는 기존 보고서 편입 심사를 통과한 뒤 위키에 발행됩니다. 원본 추출·필드 매핑·내용 심사·발행은 각각 별도 단계입니다. 매핑 성공만으로 발행하지 않습니다.

이미 `ReportRecord` JSONB 정본이 준비된 경우에는 기존 `POST /wiki/reports/{report_id}/ingest`와 `{"version":1}` 요청을 계속 사용합니다. [정본 보고서 편입](보고서-위키-편입.md)을 참고하세요. 자동 매핑 경로는 원래 보고서에 공통 필드명이 없을 때 사용하는 추가 경로이며, 상위 시스템의 JSONB를 자동으로 수정하지 않습니다.

## 요청과 서비스 경계

[패키지 README](../okf-agent/README.md)의 설치·라우터 등록·모델 설정을 먼저 적용합니다. 원본은 서버의 허용 목록이나 DB 설정으로 지정합니다.

```sh
curl --request POST http://127.0.0.1:8000/wiki/reports/REPORT-001/map-and-ingest \
  --header 'Content-Type: application/json' \
  --data '{"version":1,"source":"file"}'
```

DB 원문은 `"source":"database"`로 요청합니다. 본문에는 양의 정수 `version`과 `file` 또는 `database`인 `source`만 받습니다. 임의 파일 경로·테이블·본문·승인 상태·설비 ID 등을 추가하면 `422`입니다. 버전 문자열 `"1"`, 실수 `1.0`, 불리언 `true`, 0·음수도 거절합니다.

```python
from clew_okf import WikiAgent

agent = WikiAgent("/srv/clew/okf.local.yaml")
result = agent.map_and_ingest_report("REPORT-001", version=1, source="file")
print(result["status"], result["findings"])
print(result.get("mapping"), result["review"])
```

보고서 ID·버전은 서버가 원본에 부여한 고정 식별자를 사용합니다. `event_id`는 실제 사건을 식별하는 값입니다. 원문과 서버 메타데이터에 사건 ID가 없으면 상위 업무 시스템에서 확정한 뒤 다시 요청해야 합니다. 모델이 보고서 ID·제목·작성 시각을 조합해 사건 ID를 만들어 내지 않습니다.

`create_router()`의 인증·인가는 상위 서비스가 구성합니다. 파일 허용 목록과 DB 설정을 수정할 권한, 보고서를 확정하고 재사용을 승인할 권한도 서버 운영·업무 시스템이 관리합니다. 같은 위키의 모든 워커는 `flock`·심볼릭 링크·원자적 경로 교체를 지원하는 동일한 공유 POSIX `output` 경로를 사용합니다. 동시 요청의 출력 잠금 충돌은 `409`입니다.

## 파일 원본 설정

다음은 설정 예시입니다. 기존 설비 CSV와 서버에서 허용한 모델을 사용하고, 보고서 폴더는 일반 매뉴얼의 `documents.root`와 별도로 관리합니다. 예시 경로와 식별자는 실제 값으로 바꿉니다.

```yaml
title: CLEW 제조 위키
output: ./output
equipment_csv: ./equipment.csv
synthesis:
  endpoint: https://llm-gateway.example.internal/v1/chat/completions
  model: your-approved-model
  api_key_env: CLEW_MODEL_API_KEY
  review: true
admission:
  max_candidates: 32
  # review_model: your-approved-admission-model
  mapping:
    # model: your-approved-mapping-model
    files:
      root: ./report-originals
      kordoc: kordoc
      timeout_seconds: 120
      max_bytes: 67108864
      entries:
        - report_id: REPORT-001
          version: 1
          path: DEMO/PUMP-01/정비보고서.hwpx
          revision: "REPORT-R1"
          status: finalized
          reuse_approved: true
          metadata:
            plant_id: DEMO
            equipment_id: PUMP-01
            event_id: EVENT-001
            # supersedes_version: 1  # 새 버전이 현재 편입 버전을 대체할 때 지정
```

`mapping.model`을 생략하면 `synthesis.model`로 매핑합니다. 지정하면 같은 모델 엔드포인트에서 해당 모델을 사용합니다. 편입 심사 모델은 `admission.review_model`로 별도 지정할 수 있습니다.

`entries`에서 요청한 ID·버전이 정확히 한 항목과 일치해야 합니다. `path`는 `root` 아래의 상대 POSIX 경로입니다. 절대 경로, `..`, 심볼릭 링크를 통한 원본 연결은 허용하지 않습니다. 원본 폴더와 위키 출력 폴더도 겹칠 수 없습니다. 파일이 없거나 읽기·추출 결과를 확인할 수 없으면 편입하지 않습니다.

`status: finalized`, `reuse_approved: true`, 비어 있지 않은 문자열 `revision`은 서버 허용 목록에 저장합니다. `metadata`에는 선택적으로 `plant_id`, `equipment_id`, `event_id`, `supersedes_version`만 지정합니다. 요청자가 승인 값을 보내서 허용 목록을 바꾸는 경로는 없습니다. 변경된 보고서는 새 버전 항목으로 등록하고 기존 원본 버전도 보관합니다.

HWP·HWPX·PDF·DOCX·PPTX·XLSX는 기존 `kordoc` 추출기를 재사용합니다. Markdown·텍스트·CSV도 지원합니다. 파일의 제목·서술을 그대로 두고 필요한 값을 추출하므로 별도 Word·한글 양식을 먼저 작성할 필요는 없습니다. 다만 현재 `admission.mapping.files`에는 OCR 옵션이 없습니다. 스캔본처럼 추출할 텍스트가 없는 자료는 빈 값을 채워 통과시키지 않으며, 읽을 수 있는 원문을 준비해야 합니다. 파일 크기 기본 한도는 64 MiB이고 추출 기본 제한 시간은 120초입니다.

동일 파일을 `documents`로도 직접 수집하면 빌드를 중단합니다. 자동 매핑 원본은 매핑과 편입 심사를 통해 등록합니다.

## DB 원문 설정

기존 DB의 원문 컬럼들을 지정할 수 있습니다. DB가 처음부터 `ReportRecord`의 여덟 필드와 같은 이름으로 구성돼 있을 필요는 없습니다. 단, 설정한 원문과 서버 메타데이터에서 필요한 여덟 값을 모두 확인할 수 있어야 합니다. 다음 `database`를 위 `admission.mapping`에 추가하거나 `files` 대신 사용합니다.

```yaml
admission:
  max_candidates: 32
  mapping:
    database:
      table: wiki.original_maintenance_reports
      id_column: report_no
      version_column: report_version
      revision_column: source_revision
      status_column: workflow_state
      approval_column: reuse_allowed
      content_columns:
        - report_title
        - operating_context
        - observed_text
        - performed_action_text
        - outcome_text
      metadata_columns:
        plant_id: plant_code
        equipment_id: asset_no
        event_id: event_no
        # supersedes_version: replaces_version
      dsn_env: CLEW_RAW_REPORT_DSN
```

`table`은 `schema.table`이며 모든 컬럼명은 실제 DB 컬럼명입니다. `id_column`은 보고서 ID 문자열, `version_column`은 양의 정수, `revision_column`은 비어 있지 않은 개정 문자열을 반환해야 합니다. `status_column`의 값은 `finalized`, `approval_column`은 PostgreSQL 불리언 `true`여야 합니다. `metadata_columns`에 연결한 공장·설비·사건 ID는 공백과 슬래시가 없는 문자열이어야 합니다. `supersedes_version`은 생략·`null` 또는 양의 정수입니다.

`content_columns`는 비어 있지 않은 중복 없는 목록입니다. 지정한 컬럼 값들을 위치가 있는 원문 블록으로 변환해 모델에 전달합니다. 숫자·구조화 값도 텍스트 표현으로 읽지만, 원문에 없는 단위·적용 조건·사건 ID를 생성하지 않습니다. `metadata_columns`는 선택 사항이며 허용되는 키는 위 네 개뿐입니다. 공장·설비·사건 ID를 여기에 지정하면 서버의 확정 값으로 취급합니다. 지정하지 않은 ID는 원문에서 정확히 추출해야 합니다.

DSN은 환경 변수로 주입합니다. `dsn_env`를 생략하면 `postgres.dsn_env`, 그것도 없으면 `CLEW_POSTGRES_DSN`을 사용합니다. 계정은 해당 원본에 필요한 조회 권한을 사용하며 조회는 읽기 전용 트랜잭션입니다. 요청한 ID·버전이 정확히 한 행과 일치해야 합니다. 같은 테이블을 `postgres.records`에도 지정하면 직접 수집과 편입 심사가 중복되므로 빌드를 중단합니다.

## 추출하는 공통 필드와 한도

| 공통 필드 | 원문에서 확인할 내용 |
|---|---|
| `title` | 보고서 제목 |
| `condition` | 작업·관측에 적용된 조건 |
| `observation` | 실제 관측한 사실 |
| `action` | 실제 수행한 조치 |
| `result` | 조치 후 확인한 결과 |
| `plant_id` | 공장 ID |
| `equipment_id` | 설비 ID |
| `event_id` | 실제 사건 ID |

여덟 필드는 모두 필요합니다. 공장·설비·사건 ID는 서버 메타데이터로 확정할 수 있고, 이 경우 필드 출처에 `origin: server_metadata`를 남깁니다. 모델이 서버의 확정 ID와 다른 값을 반환하면 보류합니다. 나머지 값은 모두 원문의 연속 문자열이어야 하며 필드 값 전체가 해당 인용문 안에 정확히 포함돼야 합니다. 공장·설비 조합은 설비 마스터의 고유한 항목과 정확히 일치해야 합니다. 별칭·이름 추론이나 유일한 설비 이름으로 누락된 공장 ID를 채우지 않습니다.

필수 값이 없거나 값 자체가 `미확인`, `미기재`, `알 수 없음`, `N/A`, `NULL` 같은 자리표시자이면 `null`로 취급해 보류합니다. `미확인 부품을 제거했다`처럼 실제 사실을 담은 문장에 그 단어가 포함된 경우까지 일괄 배제하지 않습니다. 자유 요약·의역·단위 변환·문장 합성·없는 결과 채우기는 하지 않습니다.

| 한도 | 동작 |
|---|---|
| 공통 보고서의 제목·조건·관측·조치·결과 | `ReportRecord`에서 각각 최대 4,000자 |
| 근거 인용문 | 각각 최대 600자, 원문과 정확히 일치 |
| 보고서 근거 블록 | 고유 ID 기준 최대 16개 |
| 필드 매핑 입력 | 원문 전체·설비 식별 목록·메타데이터 JSON 합계 최대 64,000자 |
| 편입 심사 후보 | 같은 설비의 현재 사례 전체, 기본 32건 |
| 편입 심사 입력 | 별도로 최대 64,000자 |

자동 매핑에서는 값 전체가 600자 이내의 근거 인용에 포함돼야 하므로 더 긴 단일 값을 자동으로 잘라 통과시키지 않습니다. 입력 한도 초과도 일부 원문이나 일부 후보를 생략해 처리하지 않고 보류합니다. 여러 필드가 같은 블록을 인용하면 블록 ID·전체 본문의 SHA-256은 한 번 고정하고 필드별 인용문은 모두 따로 보존합니다.

보고서 ID·버전·확정·승인·대체 버전은 모델이 생성하지 않습니다. 이 값은 파일 허용 목록이나 설정된 DB 컬럼에서만 가져옵니다. 매핑 결과가 원문과 일치해도 모델이 관측과 결과를 잘못 분류할 가능성은 있으므로 뒤의 독립 편입 심사에서 원문·조건·설비·사건·기존 사례와 다시 대조합니다. 의미 정확도와 모든 공격 탐지를 보장하는 기능으로 해석하지 않습니다.

## 편입 이후의 페이지와 변경 검증

매핑이 성공하면 기존 편입 심사에 들어갑니다. 같은 사건 중복, 다른 사건의 보존, 명시적 개정, 근거 충돌 규칙은 [정본 보고서 편입](보고서-위키-편입.md)과 같습니다. 정상 편입된 보고서의 공통 필드는 `Maintenance Case` 페이지에, 추출된 원문 전체는 연결된 `Report Original` 페이지에 남습니다. 필드별 값이 어떤 블록·인용에서 왔는지도 사례 페이지와 원장의 `field_evidence`에 기록합니다. 원본과 사례는 `synthesize: false`이며 과거 사건을 일반 설비 적용 조건이나 절차로 재분류하지 않습니다.

`admitted_reports.json`의 매핑 기록에는 원본 종류 `kind`, 원본·승인 메타데이터의 `input_digest`, 필드별 근거 `field_evidence`, 심사 당시 같은 설비의 일반 수집 근거·설비 상태인 `dependency_digest`가 남습니다. 페이지와 원장은 같은 스냅샷에 저장되고 `current`가 한 번에 전환됩니다. 판정에 도달한 요청 기록은 `admission-decisions/`에 남습니다.

동일 ID·버전의 원본·승인·의존 근거가 유지되면 원장을 재사용하고 모델을 다시 호출하지 않습니다. 같은 ID·버전의 원본·출처가 바뀌면 충돌입니다. 편입 뒤 일반 갱신에서도 원본 파일·DB 행·승인 메타데이터와 심사 당시의 의존 근거를 다시 확인합니다. 같은 설비의 현행 매뉴얼이나 마스터가 바뀌면 기존 심사 결과를 그대로 재사용해 새 발행하지 않습니다. 변경 내용을 반영해 보고서 새 버전을 승인하고 현재 편입 버전을 `supersedes_version`으로 지정해 재검토합니다. 과거 원장과 원본 버전은 유지합니다.

## 결과 확인과 보류 처리

최종 응답의 `status`가 발행 여부를 나타냅니다. `mapping.status: mapped`는 공통 필드 추출만 통과했다는 뜻이며, 뒤의 `review.decision`이 `hold`이면 발행하지 않습니다. 이미 편입된 입력을 재사용하는 응답에는 매핑 결과가 생략되거나 `null`일 수 있습니다.

| 상황 | 처리 |
|---|---|
| 원본을 읽거나 추출하거나 승인 상태를 확인하지 못함 | `hold`, 예: `raw_source_unavailable` |
| 필수 값 누락·위조 인용·식별자 모순·매핑 모델 실패 | `hold`, 필드별 `findings` 확인 |
| 매핑 후 의미 관계나 주장 근거가 불확실함 | 편입 심사 `hold` |
| 같은 ID·버전의 원본 변경 또는 검토 중 변경 | `conflict`, 현재 발행본 유지 |
| 알 수 없는 요청 필드·임의 경로·잘못된 설정 | HTTP `422` |
| 출력 잠금 충돌 | HTTP `409` |
| 발행 단계의 실행·파일 오류 | HTTP 오류, 현재 발행본 유지 |

보류된 값을 위키 작성 과정에서 임의로 채우지 않습니다. 원본이나 상위 시스템의 확정 메타데이터를 보완하고 새 버전 규칙에 따라 다시 요청합니다. `build.wiki_reviews`는 발행한 설비 인용문의 별도 검토 결과이므로 편입 심사 결과와 함께 확인합니다. 생성 페이지의 OKF 상태는 `draft`입니다.

현재 정형 검증은 [매핑 테스트](../okf-agent/tests/test_mapping.py)와 [원문 로더 테스트](../okf-agent/tests/test_raw_report_store.py)에서 확인할 수 있습니다. 운영 적용 전에는 실제 보고서에서 필드 누락·잘못된 분류·다른 설비·별도 사건·개정 충돌의 정답을 준비해 의미 판정을 평가해야 합니다.

실제 모델로 실행한 정상·누락·오류 사례와 남은 추출 한계는 [자동 매핑 검증](자동매핑-검증-2026-11-19.md)에서 확인합니다. 모델별 단가와 합산 호출 예산은 [LLM 비용 산정](LLM-비용-산정.md)을 참고합니다.

이미 편입된 같은 ID·버전의 재사용에 멱등성을 적용합니다. 아직 편입되지 않은 보류·중복 요청은 재시도 때 매핑·심사를 다시 호출할 수 있습니다. 파일 업로드·등록과 DB의 원문 저장은 상위 서비스가 담당하며 이 엔드포인트는 서버에 등록된 원본을 조회합니다.

현재 한 요청은 보고서 한 건을 편입합니다. 현행 근거 변경으로 여러 기존 사례의 의존성이 동시에 무효화되면 발행을 중단하며, 여러 보고서의 새 버전을 한 번에 재심사하는 배치 API는 제공하지 않습니다. 원문 개정 작업은 이 재검토 범위를 함께 고려해야 합니다.
