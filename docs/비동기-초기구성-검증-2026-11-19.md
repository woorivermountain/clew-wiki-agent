# 비동기 자동 편입·초기 DB 구성 검증 — 2026-11-19

실제 uvicorn FastAPI 서버, 별도 프로세스의 워커, 합성 PostgreSQL 두 DB, 한국어 PDF·HWPX, 실제 `gpt-5.6-sol`을 연결했습니다. 초기 DB 구성·저장·업로드·보류 조회·재시작 복구를 확인했고 **회귀 테스트 195개가 통과**했습니다. 실공장 데이터의 품질·부하를 평가한 결과는 아닙니다.

## 구현된 흐름

- `POST /wiki/reports/{id}`는 텍스트 원본과 작업을 한 SQLite 트랜잭션에 저장합니다.
- `POST /wiki/reports/{id}/upload`는 HWP·HWPX·PDF를 제한된 크기로 저장하고 원본 등록과 작업을 함께 기록합니다.
- API는 작업 ID를 `202 Accepted`로 반환하고, 별도 `clew-okf worker`가 실제 추출·공통 필드 매핑·기존 편입 검증·위키 발행을 실행합니다.
- `GET /wiki/jobs/{job_id}`, `/events`, `/children`에서 상태·실제 단계·보류 이유·초기 보고서별 결과를 조회합니다. 관리형 보고서의 최신 작업은 `/wiki/reports/{id}/status?version=1`입니다.
- 상태는 `queued → running → succeeded/held/failed`이며, 초기 구성의 부모 작업은 보고서 자식들이 끝날 때까지 `waiting`입니다.
- 원문·필수 값·확정·재사용 승인을 확인하지 못한 보고서는 보류하며 현재 위키를 유지합니다.

## 첫 DB 구성의 실제 결과

`bootstrap.schemas: [factory]` 범위에서 읽기 전용으로 카탈로그를 탐색했습니다. 설비 테이블은 명시하지 않고 PK·FK로 확인할 수 있는 고유 후보를 선택하도록 했습니다.

| 항목 | 실제 결과 |
|---|---|
| 스키마 | 1개 |
| 카탈로그 관계 | 3개 |
| 컬럼 | 22개 |
| 확정한 설비 마스터 | `factory.equipment` |
| 설비 | 2대 |
| 기존 승인 보고서 작업 | 2건 |
| 기존 보고서 처리 | 정상 1건 반영, 결과 NULL 1건 보류 |
| 부모 최종 상태 | `held`, 자식 2/2 처리 완료 |

3개 관계 중 1개는 행 조회 권한이 없는 기반 테이블입니다. 이 관계는 카탈로그 정보만 읽고 행 데이터는 수집하지 않았습니다. 별도 보고서 DB에서는 설정된 원본의 ID·버전만 열거한 뒤 각 보고서를 기존 편입 심사로 처리했습니다. 승인되지 않은 행을 전체 원본 페이지로 직접 만들지 않았습니다.

탐색은 컬럼·키·주석과 설정된 승인 보고서 목록에 한정합니다. 미등록 테이블의 업무 의미·원문 컬럼을 모델이 임의로 추측하지 않습니다. 후보가 모호하거나 탐색 한도를 넘으면 보류합니다. 기존 보고서 데이터 import에는 `admission.reports` 또는 `admission.mapping.database` 설정이 필요합니다.

## 실제 HTTP·워커 사례

| 검사 | 실제 결과 |
|---|---|
| 워커 시작 전 텍스트 저장·PDF 업로드 | 모델 호출 0회 상태에서 `202`, 원본·작업 저장 |
| API 종료·재시작 후 조회 | 같은 대기 작업 유지 |
| DB 초기 기본 위키 | 설비·DB 구조·현행 매뉴얼로 생성 |
| 기존 승인 DB 보고서 | 정상 반영·NULL 보류를 각각 기록 |
| 미승인 파일·텍스트 | `awaiting_approval` 보류, 모델 호출 없음 |
| 서버 승인 후 PDF | 원문·사례 페이지 생성, `published` |
| 서버 승인 후 결과 누락 텍스트 | 필드 `result` 누락 보류, 스냅샷 모든 파일 SHA-256 유지 |
| 서버 승인 후 정상 텍스트 | 실제 반영, 후속 승인 이벤트 작업은 `unchanged` |
| 기존 주 DB 저장 완료 재통지 | 추가 모델·새 발행 없이 `unchanged` |
| 실행권 선점 후 별도 프로세스 종료 | 임대 만료 후 2번째 선점으로 완료, 같은 보고서 재발행 없음 |
| 최종 코드의 PDF 업로드·상태 조회·동일 재전송 | 최신 재시도 작업을 유지, 추가 모델 호출 0회 |

정상 텍스트는 앞서 대기하던 저장 작업이 최신 승인 상태를 읽어 먼저 반영했습니다. 승인 이벤트로 추가된 작업은 이미 편입된 같은 ID·버전을 확인해 `unchanged`였습니다. 이를 두 번 반영한 것으로 집계하지 않았습니다.

주 실행의 저장·업로드·저장 통지 4개 HTTP 요청은 이 로컬 시험에서 약 **4–17ms**에 접수됐습니다. 모델을 기다리지 않았다는 확인이며 대용량 파일 전송·운영 부하에 대한 지연 보장은 아닙니다. 진행 조회 표본의 최대 응답 시간은 0.0087초였습니다.

## 모델과 결과물 검증

실제 `gpt-5.6-sol`/`low` 호출은 **16회**였습니다. 매핑 5회, 편입 심사 3회, 설비 작성 4회, 문장 검토 4회이며 모두 HTTP 200입니다. 응답 재생·모델 대역은 사용하지 않았습니다. 별도의 단위·통합 테스트는 검증용 모델을 사용하므로 이 실제 실행과 구분합니다.

독립 OKF v0.2 검사기로 스냅샷 4개 모두 통과했습니다. 최종 위키는 **14개 파일 모두 통과**했습니다. 정상 보고서는 원문·공통 필드별 인용·리비전·해시와 함께 설비에 연결됐습니다. 생성 문서의 OKF 상태는 `draft`입니다.

## 연결 중 보완한 부분

- 업로드 경로가 기존 매뉴얼의 `kordoc` 설정을 상속하도록 보완했습니다. 수정 전 기록은 별도 폴더에 보존했습니다.
- 서버 승인 조회는 ID뿐 아니라 실제 원문 SHA-256·개정·식별 메타데이터로 만든 fingerprint가 승인 원본과 일치해야 합니다. 요청자가 승인 상태를 보내서 통과시키지 못합니다.
- 재시도 후 동일 저장·동일 승인 상태를 재전송해도 최신 상태 포인터를 과거 작업으로 되돌리지 않습니다.
- 작업 대상과 재확인 중인 의존 원본의 진행 필드를 분리했습니다.
- 활성 작업만 중복 등록을 막고, 완료 후 데이터가 바뀐 빌드는 새 작업으로 실행합니다.
- 외부 위키 발행 잠금 대기는 오류 재시도 횟수를 소진하지 않습니다. 실제 원본·모델 장애의 재시도는 기본 3회로 제한합니다.
- 대기·실행 중 설정이 바뀌면 보류하고, 초기 스캔 계획·활성 설정·자식 작업의 설정이 섞이지 않도록 고정합니다. 기존 SQL 필터의 YAML 날짜 값도 보존합니다.
- 미승인 정본·원문 변경·의존 근거 변경을 일반 실행 실패와 구분해 보류 사유를 반환합니다.

## 검증 범위와 운영 연결

현재 저장소에는 기존 업무 서버의 보고서 저장 트랜잭션 코드가 없습니다. 패키지의 관리형 저장·업로드 API는 자동 연결됐으며, 기존 주 DB를 쓰는 메인 서버에는 `install_wiki_service()`와 커밋 직후 `report_saved()` 훅을 등록해야 합니다.

관리형 저장은 원본 행·작업 등록이 한 SQLite 트랜잭션입니다. 외부 주 DB의 커밋과 SQLite 큐 등록은 별개이므로, 그 사이 중단까지 다루려면 메인 서비스의 primary outbox를 연결해야 합니다. 이 외부 outbox는 구현한 것으로 주장하지 않습니다. `/setup` 재탐색으로 설정된 범위·한도 안의 승인 보고서를 재확인할 수 있습니다.

SQLite WAL 상태 DB는 동일 호스트의 로컬 영속 디스크에서 사용합니다. 여러 호스트의 NFS 공유 큐는 지원 대상이 아닙니다. 인증·보고서별 권한·업무 승인은 메인 서비스가 연결합니다. 스캔 OCR 옵션과 임의 DB 종류 지원은 이번 기능에 포함하지 않았습니다. DB 초기 탐색은 PostgreSQL 대상입니다.

장애 시험은 실행권 선점 직후 종료한 프로세스에서 이미 편입된 보고서를 재확인하는 범위입니다. 새 위키 발행 도중 임의 위치에서 강제 종료하는 모든 경우의 exactly-once 보장을 시험한 것은 아닙니다. 일반 설비 페이지의 압력 기준 섹션 배치 조언도 편입 결과와 별도입니다. 실험은 API 과금 `usage`를 수집하지 않았습니다.

공장 원본 DB 행과 이전 HWPX·PDF의 체크섬이 일치했습니다. 검증용 API·워커·PostgreSQL·모델 릴레이는 종료했습니다.
