# CLEW 실공장 데이터 준비 체크리스트

첫 실행에는 **설비 마스터, 위키에 실을 DB 근거, 승인된 한글·PDF 원본과 설비 매핑**을 준비합니다. 설비 1~2대와 해당 설비의 현행 매뉴얼로 시작하면 연결과 개정 기준을 확인하기 쉽습니다. [복사해 쓸 YAML 예시](../okf-agent/okf.factory.example.yaml)

| 준비물 | 받아야 할 내용 |
|---|---|
| 설비 마스터 | 설비 ID, 설비명, 공장 코드, 공정 코드. 설비 모델과 현장 별칭은 선택입니다. |
| DB 조회 범위 | PostgreSQL의 `schema.table` 또는 뷰 이름, 실제 컬럼명, 컬럼 뜻·단위, 샘플 행. 실행 계정에는 DB 접속, 해당 스키마 `USAGE`, 필요한 마스터·뷰 `SELECT` 권한을 부여합니다. |
| 정비·점검 DB 행 | 행을 고유하게 식별할 ID, 공장·설비 ID, 개정번호, 승인·현행 상태, 적용일, 적용 조건, 순서가 보존된 절차, 판정값과 단위. |
| 한글·PDF 원본과 매핑 | HWP/HWPX/PDF 파일, 적용 설비 키, 개정번호, 적용일·현행 여부, 스캔 여부. 사내 문서 저장소에 개정본별 고정 링크가 있으면 함께 받습니다. |
| 실행 환경 | Python 3.11 이상, Node.js, `kordoc`, 원본 읽기 및 출력 폴더 쓰기 권한. 모델 작성·검토까지 쓰려면 공장 근거 텍스트를 처리할 수 있는 모델 엔드포인트와 모델 이름을 준비합니다. |

DB 접속 문자열은 실행 환경의 `CLEW_POSTGRES_DSN`으로 주입합니다. 모델 API 키를 사용하는 경우도 YAML에는 키를 담은 환경 변수 이름만 적습니다.

## 설비 키와 DB 컬럼

공장 코드가 있으면 연결 키는 `공장코드/설비ID`입니다. 예시는 `ULSAN/C-2100`과 `ULSAN/EQ-02`를 사용합니다. 마스터, 정비 DB 행, 파일 매핑에서 값과 대소문자를 맞춥니다. 공장 코드 없이 설비 ID만 사용하려면 데이터 전체에서 그 ID가 고유해야 합니다.

| CLEW가 읽는 값 | 예시 DB 컬럼 | 사용처 |
|---|---|---|
| `equipment_id` | `asset_no` | 마스터 필수 키 |
| `name` | `asset_name` | 페이지 제목. PostgreSQL에서 생략하면 설비 ID를 사용합니다. |
| `plant_id` · `process_id` | `plant_code` · `process_code` | 공장별 설비 구분과 공정 메타데이터 |
| `id_column` | `wiki_record_id` | 정비 뷰 전체에서 고유하고 비어 있지 않은 행 ID |
| `equipment_column` · `plant_column` | `asset_no` · `plant_code` | 정비 행을 마스터의 설비 키에 연결 |
| `revision_column` | `revision_code` | DB 행의 개정 표기 |
| `records[].columns` | `lifecycle`, `effective_on`, `inspection_condition`, `inspection_steps`, `acceptance_criteria` | 위키의 근거로 읽을 값 |

`postgres.tables`는 테이블의 컬럼·타입·키 같은 구조를 읽습니다. 정비 행의 내용은 `postgres.records`에 등록합니다. YAML의 `wiki.current_maintenance`는 **승인됐고 현재 적용되는 행을 반환하도록 DB 담당자가 만든 뷰**를 가정합니다. YAML 예시는 `filters: {lifecycle: current}`도 적용합니다. 실제 상태 컬럼과 값으로 바꾸세요. 현행 여부는 DB 뷰 또는 설정한 조건으로 정합니다. 설정된 PostgreSQL 설비 마스터가 0행이면 직전 위키를 유지하고 빌드를 중단합니다. 파일도 현행 문서 목록을 기준으로 입력 폴더에 넣고, 과거 개정은 현행 절차와 구분해서 관리합니다. 적용일은 DB 근거 컬럼이나 원문에 보존합니다.

설비 마스터를 CSV로 받을 때는 YAML에서 `postgres.equipment`를 빼고 최상위에 `equipment_csv: ./equipment.csv`를 추가합니다. 정비 DB 행을 함께 쓰면 `postgres.records`는 유지합니다. DB 입력이 없으면 `postgres` 전체를 뺍니다. CSV는 UTF-8이며 `equipment_id`와 `name`이 필수입니다.

```csv
equipment_id,name,plant_id,process_id
C-2100,공기압축기,ULSAN,UTIL
EQ-02,비전검사기,ULSAN,INSPECTION
```

## 한글·PDF 파일 달기

설정 파일을 기준으로 원본을 다음처럼 놓습니다. `documents.files`의 파일명은 `originals/` 아래 상대 경로입니다.

```text
okf-agent/
├── okf.local.yaml
└── originals/
    ├── 공용/압축기_점검매뉴얼.hwpx
    └── ULSAN/EQ-02/비전검사기_작업표준.pdf
```

- `include_only_listed: true`이면 `documents.files`에 이름이 있는 파일만 수집합니다. 폴더로 설비를 연결하는 파일도 목록에 경로를 올립니다.
- **파일별 지정**은 `equipment_ids: ["ULSAN/C-2100"]`처럼 적용 설비 키를 적습니다. 한 문서가 여러 설비에 실제로 적용되면 한 목록에 키를 여러 개 넣습니다.
- **폴더로 연결**하려면 `scope_from_path: true`를 켜고 `originals/ULSAN/EQ-02/...`처럼 둡니다. 파일별 `equipment_ids`가 있으면 그 값이 우선합니다. 연결되지 않은 문서는 원본 페이지에는 남고 해당 설비의 인용 작성에는 들어가지 않습니다.
- `revision`에는 문서 개정번호를, `source_uri`에는 해당 개정본을 다시 열 수 있는 고정 링크를 넣습니다. 텍스트가 없는 스캔본은 해당 파일에 `ocr: true`를 지정하고 추출본의 수치와 표를 원본과 대조합니다.

## 첫 빌드

`okf-agent/`에서 실행합니다. 복사한 YAML의 DB 이름·컬럼·파일 경로를 실제 값으로 바꾸고 입력과 출력 폴더를 분리합니다.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -e '.[postgres]'
npm install -g kordoc@4.24.83
cp okf.factory.example.yaml okf.local.yaml

# YAML 수정 및 CLEW_POSTGRES_DSN 주입 후 실행
clew-okf build --config okf.local.yaml
clew-okf check ./output/current
```

예시처럼 `synthesis`를 주석으로 두면 설비·원본·DB 페이지와 링크를 먼저 생성합니다. 모델 인용 및 문장별 검토를 추가하려면 해당 블록에 사용할 엔드포인트·모델을 설정한 뒤 다시 빌드합니다.

생성 후 `output/current/index.md`에서 대상 설비와 출처를 열어 봅니다. 빌드 결과의 `unmapped_documents`와 `warnings`를 확인하고, 모델을 켠 경우 `selected_quotes`와 `wiki_reviews`도 확인합니다. 첫 초안은 현행 수치와 단위, 적용 조건, 필수 점검 순서를 승인 원본과 대조합니다.
